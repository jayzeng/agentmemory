AgentMemory Eval 2.0 Strategy

Core recommendation

Do not keep stretching the current feedback suite into a benchmark.

Reclassify it as:

feedback-regression — targeted probes derived from reported issues

Then build a new evaluation program alongside it:

CodingMemoryBench — a reproducible benchmark for whether memory improves coding-agent outcomes safely and efficiently

A world-class eval must answer more than “was a marker present?” It should answer:

Did AgentMemory supply the right evidence at the right time, improve the agent’s decision or task outcome, avoid stale or unsafe influence, and do so within acceptable latency, token, and reliability budgets?

1. Define the decisions the eval must support

Every suite should exist to support an actual product decision:

  1. Can this release ship?
  2. Did retrieval improve or regress?
  3. Does semantic search beat BM25 enough to justify its latency?
  4. Is the 16K context budget allocated correctly?
  5. Does memory improve coding-agent task completion?
  6. Does it reduce repeated questions and contradictory decisions?
  7. Can untrusted, stale, or cross-project memory influence the agent?
  8. Does it work across corpus sizes, languages, agents, platforms, and qmd versions?
  9. Which product gap should be fixed next?
  10. Which marketing claims are supported by evidence?

If a metric cannot influence one of these decisions, it is probably noise.

2. North star: Useful Memory Yield

Define the north star as Useful Memory Yield:

The probability that memory supplies evidence that is relevant, current, source-grounded, safe, and causally improves the agent’s task outcome—relative to added tokens, latency, and operational failures.

Do not immediately compress this into one vanity number. Publish a six-dimensional scorecard:

Dimension Core question
Durability Was memory recorded and preserved correctly?
Retrieval Was the right evidence retrieved and ranked?
Context quality Did the final context contain useful evidence without stale or unsafe material?
Agent outcome Did memory improve the downstream task?
Safety/privacy Did memory cause leakage, prompt injection, or cross-scope contamination?
Efficiency What did the improvement cost in tokens, latency, CPU, and failures?

A single composite score can come later, after the individual metrics are validated.

3. Build a layered evaluation system

L0 — Harness and schema conformance

Tests whether the evaluation system itself is trustworthy:

  • Full runtime schema validation
  • No empty or vacuous oracles
  • Unique scenario and evidence IDs
  • Valid fixture references
  • Valid expected outcomes
  • Dataset hash and version
  • Complete environment manifest
  • Deterministic replay
  • Oracle mutation tests: deliberately break a result and prove the oracle notices

This prevents the harness from “passing” meaningless cases.

L1 — Storage and policy conformance

Fast, deterministic product invariants:

  • Concurrent writes preserve every committed entry
  • Crash during write leaves either the old or new complete file
  • Path traversal is rejected
  • Symlinks cannot escape the root
  • Trust/expiry metadata survives whitespace and line-ending variations
  • Untrusted results are filtered consistently across context and search
  • Project scopes do not leak
  • Secret redaction policies hold
  • File permissions are private
  • Metadata cannot corrupt entry boundaries
  • Distil cannot destroy curated memory without explicit consent

These should be mandatory release gates with zero tolerated failures.

L2 — Retrieval benchmark

Measure retrieval independently from the agent:

  • Keyword/BM25
  • Semantic
  • Hybrid/deep
  • Cross-language
  • Temporal conflicts
  • Entity ambiguity
  • Paraphrase distance
  • Negation
  • Multi-hop evidence
  • Source trust
  • Corpus scale
  • Distractor density
  • Recently updated versus stale index

Metrics:

  • Recall@1, @3, @5
  • Precision@k
  • MRR
  • nDCG@k
  • Stale-fact contamination rate
  • Forbidden-evidence retrieval rate
  • Cross-scope leakage rate
  • Retrieval score margin
  • Index freshness lag
  • Warm and cold latency

L3 — Context assembly benchmark

Retrieval success does not guarantee good context. Measure the actual prompt payload:

  • Evidence recall in emitted context
  • Evidence precision
  • Priority preservation under saturation
  • Token efficiency: useful evidence per 1,000 tokens
  • Duplicate evidence rate
  • Contradiction rate
  • Stale/expired inclusion rate
  • Untrusted instruction exposure
  • Section truncation behavior
  • Whether the final context remains structurally valid after truncation

This layer should directly evaluate buildMemoryContext() rather than qmd alone.

L4 — End-to-end coding-agent outcomes

This is the most important layer.

Give an agent a realistic repository task with and without memory. Example scenarios:

  • Continue an unfinished refactor from a previous session
  • Respect an architecture decision made five sessions earlier
  • Use the project-specific test command
  • Avoid a previously documented production incident
  • Apply a corrected API endpoint instead of a superseded endpoint
  • Resume after context compaction
  • Switch from Claude to Codex mid-task
  • Diagnose a bug whose root cause was learned previously
  • Avoid repeating a failed approach
  • Follow a user preference consistently

Measure:

  • Task completion rate
  • Test pass rate
  • Correct decision rate
  • Contradiction rate
  • Repeated-question rate
  • Repeated-work rate
  • Time to first correct action
  • Tool calls
  • Tokens
  • Wall-clock time
  • Human correction count
  • Unsupported-memory citation rate

The key result should be a paired delta:

Agent + no memory
Agent + base context only
Agent + BM25 retrieval
Agent + semantic retrieval
Agent + hybrid retrieval

L5 — Adversarial safety benchmark

Create an explicit Memory Red Team suite:

  • Prompt injection inside stored memory
  • Leading/trailing whitespace variants
  • Markdown/comment boundary attacks
  • Fake provenance
  • Poisoned source URI
  • Cross-project memory leakage
  • Secret-bearing memories
  • Symlink/path traversal
  • Unicode normalization attacks
  • Homoglyph metadata
  • Contradictory trusted/untrusted memories
  • qmd result from the wrong collection
  • Stale fact ranked above current fact
  • Malicious transcript import
  • Oversized files and output amplification

Metrics:

  • Attack success rate
  • Forbidden evidence exposure
  • Unsafe instruction execution rate
  • Secret exposure rate
  • Cross-scope leakage rate
  • False-positive filtering of safe evidence

L6 — Operational resilience

Run real processes under failure and scale:

  • Multiple concurrent CLI agents
  • Process kill during write
  • Disk-full simulation
  • Read-only files
  • Corrupt Markdown
  • Missing qmd
  • Hanging qmd
  • qmd non-zero exit
  • Index/model version mismatch
  • 10, 100, 1K, 10K, and 100K memories
  • 1 MB, 10 MB, and 100 MB daily logs
  • Cold and warm models
  • macOS, Linux, Windows
  • Node 20, 22, and 24

Metrics:

  • Data-loss rate
  • Recovery success
  • p50/p95/p99 latency
  • Peak memory
  • CPU
  • Search availability
  • Index lag
  • Error-reporting accuracy
  • Time to recovery

L7 — Longitudinal field evidence

Some claims cannot be proven synthetically:

  • User retention
  • How often remembered facts prevent repeated work
  • Whether users continue using the installed skill
  • How often memories become stale
  • Whether cross-agent handoffs are genuinely useful
  • Operational confidence over months

Use opt-in, privacy-preserving studies:

  • Donated anonymized traces
  • User interviews
  • Structured incident reports
  • Local summary statistics rather than raw memory
  • Quarterly benchmark refreshes based on real failures

4. Create a rigorous scenario schema

Each scenario should describe an event stream—not just a file and query.

{
  "id": "temporal.api-endpoint.001",
  "version": 1,
  "suite": "retrieval",
  "split": "holdout",
  "dimensions": [
    "temporal",
    "supersession",
    "paraphrase"
  ],
  "corpus": {
    "scale": 1000,
    "language": "en",
    "distractorProfile": "same-entity"
  },
  "events": [
    {
      "at": "2026-01-01T10:00:00Z",
      "type": "memory.write",
      "evidenceId": "endpoint-old",
      "content": "Harbor uses Gull v1."
    },
    {
      "at": "2026-02-01T10:00:00Z",
      "type": "memory.supersede",
      "evidenceId": "endpoint-new",
      "supersedes": "endpoint-old",
      "content": "Harbor now uses Albatross v3."
    }
  ],
  "query": "Which internal Harbor endpoint should this client call?",
  "relevantEvidence": ["endpoint-new"],
  "forbiddenEvidence": ["endpoint-old"],
  "expectedOutcome": "pass",
  "gate": true
}

Important design choices:

  • Use evidence IDs, not magic marker strings.
  • Separate semantic facts from exact wording.
  • Represent time, scope, source, trust, and supersession structurally.
  • Record whether a case is a release gate, benchmark metric, or known gap.
  • Store expected evidence and forbidden evidence independently.
  • Make every scenario replayable from an empty directory.

5. Use strong baselines

Every benchmark result should be compared against:

  1. No memory
  2. MEMORY.md injected without retrieval
  3. Filesystem grep
  4. qmd BM25
  5. qmd semantic
  6. qmd hybrid/deep
  7. Previous AgentMemory release
  8. Oracle retrieval, where the correct evidence is supplied directly

Oracle retrieval is especially important. It separates:

  • Retrieval failure
  • Context formatting failure
  • Agent reasoning failure

Without it, a failed task is difficult to diagnose.

General memory benchmarks such as LoCoMo and LongMemEval can provide external comparability, but they should be adapters—not the primary benchmark. AgentMemory needs a coding-agent-specific benchmark with repositories, commands, decisions, failures, and cross-session work.

6. Build a defensible dataset

Use three dataset classes.

A. Procedural synthetic scenarios

Best for:

  • Exact ground truth
  • Large-scale variants
  • Adversarial mutation
  • Temporal ordering
  • Concurrency/fault testing
  • Multilingual controls

Generate many surface forms from templates, but split by template family so test cases are not trivial paraphrases of training fixtures.

B. Curated realistic coding histories

Create realistic multi-session project histories covering:

  • Architecture decisions
  • Commands and environment details
  • Bug investigations
  • Reverted decisions
  • User preferences
  • Deployment incidents
  • Incomplete tasks
  • Cross-agent handoffs

These can be authored independently, reviewed by multiple engineers, and released under a permissive license.

C. Sanitized field cases

Collect opt-in examples derived from real failures:

  • What should have been remembered?
  • What was retrieved?
  • What did the agent do?
  • What was the correct outcome?

Never require publishing raw personal memory. Store sanitized minimal reproductions and provenance cards.

7. Prevent benchmark leakage and overfitting

Use:

  • Public development set
  • Frozen public benchmark set
  • Private rotating release holdout
  • Quarterly publication and replacement of old holdouts
  • Generator-family separation across splits
  • Canary phrases to detect accidental leakage
  • Dataset hashes in every report
  • Independent review of new holdout cases
  • Prohibition on adding a fix-specific marker and calling it a benchmark improvement

A case can move from private holdout into public regression after it has caught a real defect.

8. Judge policy

Prefer deterministic judges

Use deterministic evaluation for:

  • Evidence retrieval
  • Source identity
  • Lifecycle state
  • Forbidden content
  • File integrity
  • Security policy
  • Commands executed
  • Test results
  • Latency and tokens

Use semantic slot scoring

For answers, extract required facts:

{
  "endpoint": "albatross.invalid/v3",
  "mustReject": ["old-gull.invalid/v1"],
  "sourceEvidence": ["endpoint-new"]
}

This is much better than exact wording.

Use LLM judges only where necessary

For free-form coding quality:

  • Blind the judge to system name
  • Randomize output order
  • Use a different model family from the evaluated model
  • Require structured rubric output
  • Run judge repeats
  • Measure judge agreement
  • Calibrate against a human-labeled sample
  • Escalate disagreements
  • Record judge model/version/prompt

Never let one opaque judge score become the only release gate.

9. Apply statistical rigor

For stochastic agent tasks:

  • Pair runs on the same task, repository, model, and seed
  • Run at least 3–5 repetitions per configuration
  • Report 95% bootstrap confidence intervals
  • Report effect sizes, not only p-values
  • Use paired significance tests
  • Predefine regression thresholds
  • Separate cold and warm latency
  • Report failures and timeouts, not only successful runs
  • Preserve per-case artifacts for replay

A release should not be declared better because one aggregate score moved from 78 to 79 on one run.

10. CI and execution tiers

Pull request: under two minutes

  • Schema validation
  • Deterministic conformance
  • Security invariants
  • Tiny retrieval smoke corpus
  • Expected-baseline comparison
  • No qmd/model/network requirement

Nightly

  • Pinned real qmd
  • Corpus scale matrix
  • Concurrency and fault injection
  • Windows/macOS/Linux
  • Node LTS matrix
  • Warm/cold latency
  • Prior-release comparison

Weekly

  • Real coding-agent tasks
  • Multilingual suite
  • Randomized adversarial scenarios
  • Multiple model tiers
  • Judge calibration sample

Release candidate

  • Frozen holdout
  • Full platform and qmd matrix
  • Previous-release paired comparison
  • Safety red-team suite
  • Artifact and environment manifest
  • Human review of every statistically meaningful regression

Quarterly

  • Publish old holdout
  • Rotate new private holdout
  • Add field-derived failures
  • Recalibrate judges and release thresholds

11. Release gates

Start with explicit gates rather than a weighted score.

Mandatory zero-failure gates

  • No path/root escapes
  • No forbidden trust/lifecycle exposure
  • No cross-project leakage
  • No committed-write loss under supported concurrency
  • No corrupted file after injected process failure
  • No false success exit code for failed sync
  • All supported platforms pass conformance

Regression gates

  • Retrieval Recall@5 and nDCG cannot decline beyond a predefined margin
  • Agent task success must be statistically non-inferior to the previous release
  • No statistically significant increase in contradiction or stale-fact use
  • Token overhead must remain within budget
  • Warm and cold latency budgets must be met separately
  • Index freshness must remain within its SLO

Provisional targets can be introduced after the first stable baseline. Avoid inventing thresholds before measuring current variance.

12. Reporting

Every run should emit:

eval-results/
  report.json
  report.html
  environment.json
  dataset-manifest.json
  cases/
    <scenario-id>/
      inputs.json
      retrieved.json
      context.md
      agent-output.json
      judge.json
      timings.json

The report should show:

  • Current versus previous release
  • Current versus each baseline
  • Confidence intervals
  • Failure clusters by dimension
  • Scale/language/platform slices
  • Cold versus warm latency
  • Safety violations
  • Direct replay command for every failed case

Do not lead with one overall score. Lead with a release verdict and the six-dimensional scorecard.

13. A practical 90-day roadmap

Weeks 1–2: Eval contract

  • Rename existing suite to feedback-regression
  • Define the versioned scenario schema
  • Add expected outcomes and gating classification
  • Add environment and dataset manifests
  • Fix exact-marker false failures
  • Make evaluator behavior fully dataset-driven

Weeks 3–4: Conformance and safety

Turn every reproduced production issue into a deterministic case:

  • Traversal
  • Symlinks
  • Trust whitespace bypass
  • Cross-profile qmd
  • Unsafe direct search
  • Concurrent writes
  • Crash safety
  • File permissions
  • Metadata injection
  • Destructive distil

This becomes the first meaningful release gate.

Weeks 5–7: CodingMemoryBench Retrieval v0

Target roughly:

  • 300–500 retrieval scenarios
  • Multiple corpus scales
  • Temporal and contradictory evidence
  • Several languages
  • Hard distractors
  • No-memory, grep, BM25, semantic, hybrid, and prior-release baselines
  • Recall, nDCG, stale contamination, latency, and index freshness

Weeks 8–10: Agent outcome benchmark

Build 40–60 realistic coding tasks:

  • Resume work
  • Apply prior decisions
  • Avoid known mistakes
  • Cross-agent handoffs
  • Temporal corrections
  • Incident knowledge

Run paired memory/no-memory experiments with at least two representative model tiers.

Weeks 11–12: Holdout and publication

  • Create private release holdout
  • Publish benchmark/data cards
  • Add nightly/weekly workflows
  • Produce HTML comparison dashboard
  • Define release regression policy
  • Document exactly which product claims are supported

First three PRs

PR 1 — Evaluation foundation

  • Versioned scenario schema
  • Full validation
  • Evidence IDs
  • Expected outcomes
  • gate classification
  • Environment/dataset manifest
  • Baseline comparison report
  • Migrate current feedback cases without changing behavior

PR 2 — Production conformance suite

Convert the production audit findings into deterministic security, durability, isolation, and failure-semantics tests.

This should become the first zero-tolerance release gate.

PR 3 — CodingMemoryBench Retrieval v0

  • Realistic corpus generator
  • Temporal/conflicting evidence
  • Corpus scale tiers
  • Multilingual cases
  • BM25/semantic/hybrid/previous-release baselines
  • Recall@k, nDCG, stale contamination, and latency
  • Confidence-interval HTML report

Strategic principle

The evaluation becomes world-class when it stops being a collection of tests and becomes a measurement system for product decisions:

  • It distinguishes correctness from quality.
  • It distinguishes retrieval failure from agent reasoning failure.
  • It measures causal task improvement, not merely recall.
  • It treats safety and data integrity as first-class outcomes.
  • It is statistically defensible and reproducible.
  • It catches regressions without being permanently red.
  • It can support—or falsify—public product claims.

Executable App Semantics & Continuous Agent Learning

A consolidated design for extending AgentMemory with structural app models, executable agent skills, normalized experience capture, evidence-bounded learning, and safely validated behavioral improvement—while keeping the AgentMemory core local, inspectable, and intentionally boring.

Verdict

The architecture has a sound center: keep AgentMemory small, represent app locality explicitly, treat sessions as evidence, and mutate behavior through reversible overlays. The original proposal was too broad to implement safely in one MVP and treated Slack threads as a universal parent. This revision corrects the scope model and puts delivery gates ahead of framework generation.

Build now: one deterministic Pi + Slack replay path from recurring correction to a validated, revision-checked policy candidate. Add live bindings and an LLM reviewer only after the replay suite is stable.

Core thesis

The agent system learns without turning the base model—or AgentMemory core—into the learning engine.

MCP exposes capabilities. App Skills encode executable application semantics. AgentMemory preserves durable knowledge. Observation preserves experience. Learning converts bounded evidence into candidate improvements. Evals and intervention ledgers decide what survives.

The crucial distinction is that application locality—such as Slack's workspace → channel → conversation → message operational path—is not merely metadata. It is an executable projection of the world the agent is operating in. That model should teach the LLM how to navigate context, select the right scope, invoke operations, and reason about locality without claiming to replace the application's complete domain ontology.

1 · Preserve the original boundary

AgentMemory remains the durable knowledge substrate—not an autonomous platform.

The existing AgentMemory design is unusually compatible with this proposal because its core is deliberately small: inspectable Markdown remains authoritative, qmd is optional/disposable, information is separated by lifetime, and the intelligence around the files can be replaced without taking the memory with it.

Core owns

  • MEMORY.md: curated durable facts and decisions.
  • daily/YYYY-MM-DD.md: append-oriented work evidence.
  • topics/*.md: longer-lived threads with links to evidence.
  • SCRATCHPAD.md: short-lived checklist state.
  • Read/write/search/context APIs and optional qmd retrieval.

Core should not own

  • Automatic ingestion of every transcript.
  • Slack/GitHub/Gmail ontologies.
  • Autonomous mutation of skills.
  • Hosted databases or cloud replication.
  • Opaque semantic graphs required for correctness.
  • A daemon/agent runtime merely to make memory work.
The core should protect ownership. Intelligence should be optional.

A background reviewer, cron job, harness hook, or external learning package may review sessions, propose durable facts, prune stale entries, or learn better procedures—but that is an extension of AgentMemory, not a reason to make the core autonomous.

2 · Executable application semantics

Turn predefined app layers into code the LLM can actually use.

Slack's literal object graph branches: a top-level message belongs directly to a channel, while a reply belongs to a thread. A single-parent runtime path should therefore use a normalized conversation scope:

flowchart TD
  W["Workspace"] --> C["Channel"]
  C --> V["Conversation<br/>kind: channel | thread"]
  V --> M["Message"]
  C -.->|top-level Slack messages| VC["channel conversation"]
  C -.->|thread_ts| VT["thread conversation"]
  VC -.-> V
  VT -.-> V

The operational hierarchy carries contextual priors: a thread conversation is normally more local and relevant than channel history; channel context is more local than workspace-wide knowledge. The source event still retains Slack's raw IDs. An LLM should not need to rediscover this routing rule from raw MCP tools every time.

Do not encode a convenient falsehood. workspace → channel → thread → message rejects ordinary top-level messages or invents fake threads. The conversation projection gives retrieval and authorization one valid path for both cases.

2.1 AppDefinition

export interface AppDefinition<Event = unknown> {
  id: string
  version: string

  layers: LayerDefinition[]
  operations: OperationDefinition[]
  policies?: AppPolicy[]

  normalize(input: unknown): Event
  resolveScope(event: Event): ScopePath
}

export interface LayerDefinition {
  id: string
  parent?: string
  identity: { fields: string[] }
  searchable?: boolean
  addressable?: boolean
  terminal?: boolean
}

export interface ScopeRef {
  app: string
  layer: string
  id: string
  name?: string
  parent?: { layer: string; id: string }
}

type ScopePath = ScopeRef[]

Slack becomes executable TypeScript rather than merely a schema:

export const slack = defineApp({
  id: "slack",
  version: "1.0",
  layers: [
    { id: "workspace", identity: { fields: ["team_id"] } },
    { id: "channel", parent: "workspace", identity: { fields: ["channel_id"] } },
    { id: "conversation", parent: "channel", identity: { fields: ["kind", "id"] } },
    { id: "message", parent: "conversation", identity: { fields: ["ts"] }, terminal: true }
  ],
  normalize(raw) {
    return {
      ...raw,
      conversation: raw.thread_ts
        ? { kind: "thread", id: raw.thread_ts }
        : { kind: "channel", id: `channel:${raw.channel_id}` }
    }
  },
  resolveScope(event) {
    return [
      scope("workspace", event.team_id),
      scope("channel", event.channel_id),
      scope("conversation", event.conversation.id, { kind: event.conversation.kind }),
      scope("message", event.ts)
    ]
  }
})

2.2 Scope and entity are different

Keep operational locality separate from semantic relationships. A conversation is structurally scoped to a channel and workspace but may semantically relate to a project, person, incident, customer, or service.

flowchart TD
  W["Workspace"] --> C["Channel"]
  C --> V["Conversation"]
  V --> M["Message"]
  V -.->|semantic| P["Project"]
  V -.->|semantic| U["Person"]
  V -.->|semantic| I["Incident"]
  V -.->|semantic| S["Service"]
Scope = where something happened. Entity = what it is about. Memory = what should be remembered.

2.3 Hand-author first; compile only proven repetition

The future target is two generated products, but a compiler is not part of the first slice. Hand-author the Slack definition, semantic façade, and progressive instructions. Revisit generation only after a second app demonstrates the same stable contract.

flowchart LR
  DEF["AppDefinition"] --> SKILL["Progressively disclosed SKILL.md<br/>How the app works"]
  DEF --> SDK["Executable semantic SDK<br/>How to operate in it"]
  SKILL --> LLM["LLM"]
  SDK --> LLM
  SDK --> BIND["Binding"]
  BIND --> MCP["MCP"]
  BIND --> REST["REST API"]
  BIND --> CLI["CLI / local tools"]

The LLM-facing surface should look like app semantics rather than transport semantics:

import slack

channel = await slack.channel("agent-memory")
thread = await channel.thread("1754833021.123")

context = await thread.context()
decision = await thread.find_decision()
await thread.reply("...")

thread.find_decision() may internally combine Slack API calls, AgentMemory retrieval, pinned/canonical references, ranking, authorization checks at every widened scope, and structured result validation. The agent programs against Slack semantics; MCP or REST remains an interchangeable capability binding.

2.4 Customization through overlays

Distributed app definitions should be immutable base code. User and learned customization should be overlays:

extends: slack@1

layers:
  canvas:
    action: add
    parent: channel

  huddle:
    action: add
    parent: channel

  message:
    action: update
    searchable: false

“Delete” should normally mean disable rather than destroying the base definition. Precedence:

base package < validated learned overlay < explicit user override

A learning system must never silently outrank an explicit user choice.

3 · What Better Harness teaches us

Make the LLM one probabilistic stage inside a deterministic evidence protocol.

Better Harness contributes the strongest design ideas for post-execution learning. The main takeaway is to avoid a loose session → LLM reflection → memory pipeline.

3.1 Learn from Experience Episodes, not whole sessions

A single host session may contain multiple distinct tasks, app scopes, or goals. Normalize heterogeneous host events and segment them into versioned episodes.

interface ExperienceEpisode {
  id: string
  host: "pi" | "prime" | "claude" | "codex" | "cursor"
  app?: string
  scope?: ScopePath
  intent?: string
  events: AgentEvent[]
  outcome: {
    completed?: boolean
    corrected?: boolean
    validated?: boolean
  }
  evidenceRefs: EvidenceRef[]
}

3.2 Host adapters and AppDefinitions are orthogonal

flowchart TD
  PI["Pi"] --> HA["HostAdapter"]
  PR["Prime Agent"] --> HA
  CL["Claude"] --> HA
  CO["Codex"] --> HA
  HA --> EV["Normalized execution events"]
  EV --> AD["AppDefinition scope resolver"]
  AD --> EP["Experience Episodes"]
  S["Slack"] --> AD
  G["GitHub"] --> AD
  GM["Gmail"] --> AD

HostAdapter: how to interpret an execution trace. AppDefinition: what world that execution happened in. This avoids an N×M integration explosion.

3.3 Observation Manifest

“Not observed” must never silently become “did not happen.” A learning run should record source availability, eligible episodes, analyzed episodes, sampling strategy, coverage, truncation, and warnings.

interface ObservationManifest {
  sources: {
    id: string
    status: "observed" | "partial" | "unavailable"
  }[]
  eligibleEpisodes: number
  analyzedEpisodes: number
  selection: "all" | "stratified" | "latest"
  coverage: "high" | "medium" | "low"
  warnings: string[]
}

3.4 Bounded evidence packet + match/abstain

flowchart LR
  EP["Experience episodes"] --> DET["Deterministic detectors / grouping"]
  DET --> PACK["Bounded ReviewPacket"]
  PACK --> LLM["LLM reviewer"]
  LLM -->|match| VAL["Deterministic validator"]
  LLM -->|abstain| STOP["No candidate"]
  VAL --> CAN["LearningCandidate"]

The reviewer should only reference allowlisted episodes/evidence and should be able to abstain. Unsupported evidence references or unsupported pattern types should fail validation.

3.5 Durable owner routing

Memory is one possible output of learning, not learning itself.

Observed problemDurable owner
Repeatedly rediscovered fact or decisionAgentMemory
Recurring behavioral correctionApp policy / skill overlay
Skill exists but is not invokedSkill routing
Existing memory is stale/conflictingMemory supersede/update
App world model is missing a structural conceptAppDefinition overlay
New behavior could regress existing behaviorEval
Invariant that must never be violatedDeterministic gate

3.6 Skill maturity is evidence-backed

Present → Routed → Exercised → Validated → Outcome-supported

An app policy merely existing does not mean the model noticed it, applied it, applied it correctly, or improved outcomes. The post-session learner should diagnose which stage failed.

3.7 Intervention Ledger

A changed policy is not automatically “learning.” It is an intervention until comparable future evidence supports or rejects it.

interface Intervention {
  id: string
  candidateId: string
  asset: string
  baseline: MetricSnapshot
  primaryMetric: MetricDefinition
  guardrails: MetricDefinition[]
  comparisonWindow: ComparisonWindow
  revertCondition: Condition
  result: "pending" | "improving" | "unchanged" | "regressing" | "outcome-supported"
}
Self-modification becomes experimental adaptation: baseline → candidate → canary → comparable evidence → retain or revert.
4 · What Prime Agent teaches us

Represent the agent's operating state explicitly, mutate it transactionally, and keep execution runtime separate.

Prime Agent contributes the strongest ideas for during-execution state, programmatic integrations, long-horizon goals, mutation planning, rollback, and durable addressability.

4.1 Programmatic integration objects

Rather than exposing every external operation as a top-level tool, Prime's integrations can be discovered and used programmatically. This strongly supports the AppDefinition compiler producing an executable semantic SDK in addition to instructions.

4.2 Progressive disclosure

Only lightweight skill metadata needs to be present in default context. The full semantic instructions and executable APIs should load when the app or skill is relevant. This avoids bloated prompts as the number of known apps grows.

4.3 Immutable base + mutable supplemental state

Prime's refinement model distinguishes immutable base behavior from mutable supplemental prompt/memory/skill/subagent state. For AgentMemory apps, the analogous rule is:

Base AppDefinition = immutable package code
Learned behavior   = mutable overlay
User customization = mutable explicit override

4.4 Plan → check → apply → rollback

flowchart LR
  C["LearningCandidate"] --> P["PLAN candidate overlay<br/>no mutation"]
  P --> E["Run offline evals"]
  E --> R["Re-read current state"]
  R --> Q{"Base revision<br/>still matches?"}
  Q -->|no| X["Reject / re-plan"]
  Q -->|yes| A["APPLY transaction"]
  A --> H["Record before / after + evidence"]
  H --> I["Intervention Ledger"]
  I --> RB["Rollback available"]

The planning LLM should never directly edit the durable state it used as its baseline. Application must happen through a deterministic transactional layer with revision checks.

4.5 Goal is separate from continuation

Prime distinguishes the durable goal from the policy deciding whether another autonomous turn should run. That improves learning evidence because “the agent stopped” is not the same as “the goal was completed successfully.”

interface EpisodeOutcome {
  goal?: GoalRef
  status: "completed" | "abandoned" | "failed" | "interrupted" | "unknown"
  validations: ValidationResult[]
  userAccepted?: boolean
  userCorrected?: boolean
}

4.6 Bounded autonomy and gates

Long-horizon execution should be bounded by turns/tokens/time and can require explicit validation gates before successful completion. We should reuse the same idea for learned behavior: a candidate must pass eval gates, then a bounded canary, then future comparable outcomes.

4.7 Stable agent identity and communication topology

Prime's subagents have durable identities and bounded family communication. For future app-to-app or agent-to-agent systems, addressability and communication boundaries should be explicit state, not anonymous prompt calls.

interface AgentRef {
  id: string
  role: string
  app?: string
  scope?: ScopePath
  capabilities: string[]
}

4.8 Negative lesson: do not copy weak mutable-state synchronization

A mutable JSON file plus mtime-based reload is not a sufficient multi-writer protocol. Learned state may be touched by observers, review workers, users, and runtime adapters. Use append-only events and revisioned compare-and-swap semantics from day one.

4.9 Reward hacking is a first-class design risk

A self-improving loop that retains anything that raises a scalar metric can learn to optimize the wrong thing. Promotion must require multiple dimensions:

Outcome satisfied
AND policy compliance satisfied
AND safety/provenance satisfied
AND regression gates passed

Define small contracts so each part can be replaced independently.

6.2 ExperienceEvent

interface ExperienceEvent {

  occurredAt: string
  ingestedAt: string
  host: string

  parentEvent?: string

Ingestion invariant: minimize, redact, classify trust, and enforce retention before appending an event. Provenance records origin; it does not grant trust.

6.3 Protocol invariants

  • Event IDs and idempotency keys are stable across replay; duplicate ingestion has no effect.
  • Every persisted record declares a schema version and migration path.
  • Every scope transition is validated against an AppDefinition and authorized by the binding.
  • Reviewers may cite only evidence references present in their bounded ReviewPacket.
  • Free-form app content may inform a proposal but never becomes generated executable code.
  • User overrides always outrank learned state; app/global promotion always requires maintainer review.

6.6 AgentMemoryBridge

class AgentMemoryBridge {
  async propose(candidate: LearningCandidate): Promise<MemoryProposal> {
    return validateAndEncode(candidate) // no durable write
  }

  async applyApproved(proposal: MemoryProposal, approval: Approval) {
    verifyApproval(proposal, approval)
    return memoryWrite({ target: proposal.target, content: proposal.markdown })
  }

  async search(query: string) {
    return memorySearch({ query, mode: "keyword" })
  }
}

The bridge separates proposal from application. The first slice does not auto-write long-term memory.

7 · Continuous learning protocol

Sessions are evidence, not memory.

The learning layer may read session traces, but it should never blindly promote raw transcript content into durable knowledge or executable behavior.

7.1 Initial learning patterns

Implement recurring correction first. Add repeated rediscovery as the second MVP-exit demonstration only after the behavior path passes its negative controls.

Repeated rediscovery

The agent repeatedly spends effort reconstructing a durable fact or decision.

Likely owner: AgentMemory.

Recurring correction

The user repeatedly corrects the same behavioral mistake or routing choice.

Likely owner: app policy or skill overlay.

7.2 Example: Slack decision retrieval

Experience:
  User: "What did we decide?"
  Agent: searches workspace first; returns wrong discussion.
  User: "No, I mean the decision in this thread."

Detector:
  recurring-correction on target slack:decision-retrieval

Candidate:
  when intent = decision_lookup
  when conversation.kind = thread
  prefer conversation → channel → workspace

Generated eval:
  context has conversation { kind: thread, id: TH1 }
  request = "What did we decide?"
  expected first_search_scope = conversation

Intervention:
  baseline accuracy = measured
  candidate enabled for bounded comparable episodes
  guardrails include tool-call count and user corrections

Outcome:
  retain if supported; revert if regression

7.3 Learning scope

Learning itself must be scoped so private local behavior does not contaminate distributed base apps.

instance      app-instance / workspace / channel specific
user          behavior/preferences across one user's apps
organization  organization-level conventions
app           generic reusable behavior for Slack/GitHub/etc.
global        generic agent behavior

Automatic promotion should normally stop at instance/user scope. App/global promotion should be deliberate maintainer action.

8 · Persistence & concurrency

Use a revisioned local journal with a concrete commit protocol—not mutable shared JSON.

Observation data and learned-state mutations benefit from the same property AgentMemory values: preserve history rather than silently overwrite it. The MVP supports concurrent processes on one local machine; it does not claim distributed consistency.

8.3 Compare-and-swap

plan.baseRevision = 103

apply(plan):
  if currentRevision != 103:
    reject conflict / re-plan
  else:
    append seq 104 atomically
    materialize effective snapshot

CAS gives deterministic conflict detection, but safety also requires a real commit protocol:

  1. Acquire a per-app exclusive writer lock with stale-lock recovery.
  2. Re-read the current revision and validate the complete plan.
  3. Append one length-delimited, checksummed record; flush according to the documented durability mode.
  4. Materialize snapshots through temporary-file write + flush + atomic rename.
  5. On recovery, accept only complete checksummed records and rebuild the snapshot from the journal.

This provides auditable single-machine multi-process writes. Network filesystems and multi-machine writers remain out of scope until the journal is replaced by a store with explicit distributed transaction semantics.

8.4 Privacy boundary

flowchart LR
  RAW["Raw session<br/>ephemeral evidence"] --> SAN["Sanitized normalized episode"]
  SAN --> REF["Bounded evidence references"]
  REF --> C["Learning candidate"]
  C --> D["Durable artifact"]

Default policy: do not copy raw sessions; persist only schema-allowlisted fields; redact credentials before the ledger; keep free-form evidence for the shortest configured window; support deletion by subject/source with tombstones; and ensure derived candidates cannot outlive required evidence unless they retain an approved, sanitized summary.

9 · Threat model

Treat apps, transcripts, and learned state as separate trust zones.

Poisoning through one anomalous sessionIndependent-session floors, negative controls, scope-limited candidates, human review for higher scopes.One session produces no recurring-correction candidate.
Concurrent or partial state writesWriter lock, CAS, framed checksummed records, flush policy, crash recovery.Stale plan and truncated-tail tests fail safely.
Reward hacking / metric gamingPrimary outcome plus policy, safety, provenance, cost, and correction guardrails.Any guardrail regression blocks promotion even if the primary metric rises.
Authorization is not part of AppDefinition inference. The semantic layer can request a wider scope; only the capability binding may authorize and execute it.
10 · Recommended MVP

Prove one behavior path first; earn the broader framework.

The implementation order is intentionally narrower than the final architecture. It starts with deterministic replay and a single supported candidate shape, then adds persistence, live read-only bindings, and finally the knowledge-learning demonstration.

Host

Pi replay first. Export only the allowlisted fields needed by the fixture schema; do not copy raw sessions into a new store.

App

Slack read-only first. Normalize channel and thread conversations, but keep authorization in the binding.

First pattern

Recurring correction only. Add repeated rediscovery after the policy path passes its negative controls.

Acceptance criteria

  • One correction session never qualifies as a recurring pattern; two independent matching sessions may qualify.
  • Unknown, deleted, modified, or out-of-packet evidence rejects the candidate.
  • App text—including prompt-injection-like text—cannot become executable policy or change owner routing.
  • Conversation-first search widens monotonically and re-authorizes each scope.
  • Duplicate event replay and duplicate plan application are idempotent.
  • A stale plan, partial journal record, failed offline eval, or guardrail regression cannot mutate effective state.
  • Every intervention can identify its baseline, candidate, evidence window, result, and exact revert operation.
  • The first slice requires no AgentMemory core changes; any future core change gets a separate compatibility decision.

Two MVP-exit demonstrations

A · Learn behavior

  1. Two independent episodes correct overly broad Slack search.
  2. Detector creates a structured conversation-first candidate.
  3. Validator proves evidence sufficiency and locality.
  4. Offline eval passes; policy enters bounded canary.
  5. Comparable outcomes either support promotion or trigger revert.

B · Propose knowledge

  1. Agent repeatedly reconstructs the same durable decision.
  2. Detector links independent evidence and routes to AgentMemory.
  3. Bridge produces sanitized Markdown with provenance—without writing it.
  4. A user or configured approval policy accepts the proposal.
  5. Next session retrieves the approved fact instead of reconstructing it.

Explicit non-goals for MVP

  • A general AppDefinition compiler, app marketplace, or generated SDK.
  • Slack write operations, organization/app/global auto-promotion, or generated executable code.
  • Multi-machine writers, cloud sync, or a hosted learning service.
  • Proving behavior improvement from a scalar benchmark alone.

11 · Design principles

The guardrails that keep the architecture coherent.

Sessions are evidence, not memory.Review them externally. Promote only selected durable outputs.
App structure is executable.The LLM should be able to program against an app's semantics, not only raw tools.
Transport is replaceable.MCP, REST, CLI, or local bindings sit beneath a stable semantic operation layer.
The core stays boring.AgentMemory remains local Markdown + retrieval, not a daemon or autonomous platform.
Missing evidence is data.Coverage, truncation, unavailable sources, and sampling must be explicit.
The LLM may abstain.Bound evidence and validate output references rather than inviting unconstrained reflection.
Memory is one durable owner.Behavior may belong in skills, routing, app policy, app schema, evals, or gates instead.
Intervention is not learning.A candidate becomes learned behavior only after comparable outcome evidence supports it.
Base code is immutable.Learning generates overlays with explicit precedence and rollback.
Writes are revisioned.Use append-only journals and CAS; avoid shared mutable JSON and mtime-based synchronization.
Goals need real completion evidence.A stopped turn is not proof that the task succeeded.
Optimize under guardrails.Outcome improvement alone is insufficient; policy, safety, provenance, and regressions matter.

Knowledge State answers “What do I know?” via AgentMemory. World/Semantic State answers “How is this application structured?” via AppDefinition. Behavioral State answers “How should I operate here?” via learned policies and skills.
